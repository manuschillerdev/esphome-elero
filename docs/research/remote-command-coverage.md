# Physical remote commands and hub coverage

The hub covers normal movement, short steps, preset recall, basic light control, and position polling. It also sends the three steps for basic pairing. **Full coverage of receiver functions is still open.** The clearest gaps are writing and clearing receiver presets, changing receiver Auto/Manual mode, and managing learned radio links. The manuals establish these effects. They do not establish how many additional radio commands they require.

This review compares the [17 manuals and the programming guide](../manuals/README.md) with firmware revision `6abd2c4`. Page numbers below refer to the local English PDFs. All 552 host unit tests passed at that revision. No receiver was operated for this review.

## How to read the comparison

A **primitive** is a radio operation the hub must be able to send. Its packet type, destination, and timing can matter as much as its command byte. A **sequence** uses existing primitives to achieve the required receiver effect. Opening a blind to a chosen height and saving that height in the receiver are two different effects. Only the second must survive later operation from another remote.

- **Sends** means a firmware path builds and queues the operation. Hardware evidence applies only to the receiver and action tested.
- **Sequence** means the steps are available. The table states any limit on receiver behavior or on timing.
- **Open** means the receiver effect has no established mapping in the project. A button chord (two or more buttons held together) can produce one radio message, several messages, or a change inside the remote.
- **Local** means the feature can run on the remote or in an automation. Any radio effect that still needs evidence is listed separately.

## Radio operations the hub sends

The first hex number in each row is the packet **type**. The second is the decoded **command**. These are separate fields. A selector identifies a remote channel. A targeted packet identifies one receiver by its 24-bit address. These are the default encodings. A device can have command overrides. [Packet definitions](../../components/elero/elero_packet.h) · [Packet builders](../../components/elero/elero_packet.cpp) · [Device overrides](../../components/elero/nvs_config.h)

| Receiver operation | Type / command | What the firmware does |
|---|---|---|
| Press UP or DOWN | `44 / 20`, `44 / 40` | Sends a channel button command. A roller shutter can run to its end position. A Venetian receiver can move one step. Other receivers on the learned channel can respond. |
| Release a button | `44 / 00` | Ends the explicit short press or freezes dimming. The short-press action queues three press packets and three release packets. These repeats implement **one** tap. |
| Run fully up or down | `6A / 21`, `6A / 41` | Addresses one cover. Step-receiver mode uses these for ordinary Open/Close. A VarioCom recording shows short DOWN followed by targeted long DOWN. A separate hardware report supports sending the targeted command directly. [Capture and test references](../TESTING_STEP_RECEIVERS.md#rf-capture-evidence-and-limits) |
| Stop | `6A / 10` for covers, `44 / 10` for the light STOP path | The cover path cancels pending commands, sends STOP and requests status. During timed dimming the hub sends a button release. |
| Recall preset 1 | `44 / 44` | Requests the stored intermediate position. Action name in the project is `int`. |
| Recall preset 2 | `44 / 24` | Requests the stored ventilation, fabric-tension or slat position. Action name is `tilt`. |
| Request receiver status | `6A / 00` | CHECK polls a receiver. The hub decodes position, motion, faults and light states from status reports. A targeted CHECK and a channel button release share a command byte. |
| Start basic single-channel pairing | `70 / 80` | Sends P for the selected channel. The pairing manager can then send channel UP and DOWN as two separately confirmed steps. |

Implementation and software tests: [device registry](../../components/elero/device_registry.cpp) · [command queue](../../components/elero/command_sender.h) · [pairing manager](../../components/elero/learn_in_manager.cpp) · [packet tests](../../tests/unit/test_packet_vectors.cpp) · [registry tests](../../tests/unit/test_device_registry.cpp). A raw transmit facility or a configurable command byte gives no evidence for the meaning of an unknown command.

## Pairing and deleting radio links

| User action or receiver effect | Coverage | Evidence and limits |
|---|---|---|
| Pair the first channel after the receiver enters learning readiness | **Sequence implemented.** Single-channel P, UP on upward travel, DOWN on downward travel. | The initial power cycle is external to the radio protocol. The manager waits for each user confirmation. It declares completion after transmission. Independent control after pairing is the acceptance test. Some COM/Son instructions allow the first matching direction to be DOWN. The manager implements UP first. [AstroTec bidi p. 25](../manuals/en/astrotec-868.pdf#page=25) · [COM p. 2](../manuals/en/com-series.pdf#page=2) · [pairing tests](../../tests/unit/test_learn_in_manager.cpp) |
| Open learning readiness from an already paired remote | **Open**, both asynchronous and synchronous variants. | UP + DOWN + P opens ordinary readiness. DOWN + P can open synchronous readiness. The already paired remote performs this step. The new remote then sends P and the direction confirmations. Knowing those final steps leaves the first operation unresolved. Power cycling can provide ordinary readiness for an additional remote. It does not reproduce the already paired remote’s radio request. [Programming guide p. 2](../manuals/en/transmitter-programming.pdf#page=2) · [COM p. 2](../manuals/en/com-series.pdf#page=2) |
| Select one receiver for pairing, next or previous receiver | **Open.** | S selects from ready receivers. Another press selects the next. A brief press followed by a longer one selects the previous receiver. Group P (`45 / 81`) and targeted P (`6A / 84` and `69 / 84`) were observed in other contexts. Neither observation establishes an S mapping. The project documents these variants for reception only. ## Double presses and public firmware evidence

**The VarioCom double press has an observed command value in each direction.** An owner of a VarioCom 284450002 read the commands from the radio debug log and checked the blind's movement. An independent eleropy user reported successful Tilt and Int operation on normal and step receivers. These are hardware reports. The VarioCom author published complete example log lines for short and held DOWN. The double-tap results in that thread are a table of observed command values. They do not give every frame of either double tap. [VarioCom observations](https://github.com/andyboeh/esphome-elero/issues/4) · [Model and tilt recheck](https://github.com/andyboeh/esphome-elero/issues/4#issuecomment-2128590751) · [Example packet sequences](https://github.com/andyboeh/esphome-elero/issues/4#issuecomment-2129977456) · [Independent receiver test](https://github.com/stanleypa/eleropy/issues/5#issuecomment-1907562655)

| Physical action | Command seen | Result on the reported VarioCom installation |
|---|---|---|
| Tap UP once / tap DOWN once | `0x20` / `0x40` | Short movement in the selected direction. |
| Double-tap UP | `0x24` | Recalls the individually saved slat position. |
| Double-tap DOWN | `0x44` | Moves down and restores the saved slat position on these blinds. On other receivers this requests the intermediate position. |
| Hold DOWN | `0x40` then `0x41` | The published trace changes from a channel packet to a targeted full-travel packet. This demonstrates that a single physical gesture can change both the command and the addressing. |

Elero also publishes an **Easy Control Transmitter Stick** interface. In its developer ZIP, `Easy Control Transmitter Stick.pdf` lists `0x24` and `0x44` as the USB key values for tilt/ventilation and intermediate position. The VarioCom log independently connects those values to the radio actions. The USB document describes the host interface. It does not specify the timing or the complete radio exchange. [Elero developer downloads](https://www.elero.com/en/downloads-service/apps-and-programs/other-programs)

The developer kit also includes an extended client that encodes combined keys, hold duration and double taps. It gives a concrete byte-level comparison for the open actions. [Developer kit payloads](developer-kit-payloads.md)

**Candidates outside the named firmware commands.** A Combio III-868 JA Pulse owner reported using targeted command values `0x25` for tilt and `0x45` for intermediate. The same owner later identified `0x24` as the correct tilt setting. There is no labelled press-to-release trace for the proposed pair in that report. Keep `0x45` as a receiver-specific intermediate candidate and `0x25` as conflicting evidence. Neither establishes the encoding for a double press **and hold** on a Pulse Plus. The current hub has a tilt byte override. It has no separate intermediate byte override, and overriding tilt alone does not select the targeted packet format in the report. Packet **type** `0x45` used for groups is a separate field. [JA Pulse report](https://github.com/andyboeh/esphome-elero/issues/1#issuecomment-1956567857) · [Later correction](https://github.com/andyboeh/esphome-elero/issues/1#issuecomment-1958821842) · [Hub command and packet selection](../../components/elero/nvs_config.h) · [Earlier project research](https://github.com/manuschillerdev/esphome-elero/issues/81)

A MonoTec owner also logged packet **type** `0xD4` during pairing. That is a lead on a different packet format. The published log does not establish the command meaning, sender role or a required transmit sequence. Its `0xCA` records fit the hub's status format. A status report during a button press cannot identify the command the remote sent. [MonoTec report](https://github.com/andyboeh/esphome-elero/issues/34) · [Project packet definitions](../../components/elero/elero_packet.h)

**Firmware search, 2026-11-21.** No public manufacturer firmware image or source release for a handheld or wall remote in this index was found in the Elero English and German download searches, the public software listings, or the GitHub projects checked. The Transmitter Stick ZIP contains three PDFs and two Windows programs. The Son NFC app transfers user settings. MultiTel 2 can display a firmware version, and MultiTec Touch documents its USB socket as a power input. None of those sources supplies a remote image. Service-only availability remains unknown. **Test for two-tap equivalence.** Use a receiver with a saved preset clearly different from both end positions. Start from the same position before each trial. Compare (1) the physical double tap, (2) one hub preset recall, and (3) two hub short presses, each with its own release, at the spacing measured in trial 1. Record all packets and the final height and slat angle. Repeat for the other direction. With a MultiTel timed fallback, record that setting too. The published results support trial 2 on the reported receivers. Trial 3 remains open. Repeated copies with the same counter are part of one transmission and cannot stand in for the two taps.

## What would settle the open mappings

1. **Preset writes and clears.** On the same receiver, compare ordinary movement + STOP, hold-direction-and-add-STOP, and simultaneous direction + STOP. Record press, overlap and release times. Move away, then recall from a second paired remote. Check each preset separately. This distinguishes stopping from writing or clearing memory.
2. **Receiver mode and priority.** Record a short mode query, set Manual, set Auto, and send the same timer action with priority off and on. Check mode from a second control. Record the receiver reply and its response to the next timer event. A single UP movement is insufficient evidence.
3. **Slider and pulse length.** Compare a button tap, a held button, and slide/hold/release on one channel. Record final movement or brightness and any replies. For JA Pulse, check the next short step from another remote after changing the setting.
4. **Pairing and groups.** Record the original transmitter and the new transmitter separately. Mark readiness, P or S, direction confirmations and cancellation. Use a spare receiver for single-link and all-link deletion. Check which previously paired remotes still work. Compare single, group and all-channel actions with the same members.

For each comparison, keep the receiver model, remote model, initial state, raw frames, timestamps and final receiver state together. Compare packet type, address, selector list, command, other payload fields and repeat timing. Count a feature as covered by a sequence when the hub produces the required result, including any lasting state change. A different packet trace can still produce an equivalent result.
